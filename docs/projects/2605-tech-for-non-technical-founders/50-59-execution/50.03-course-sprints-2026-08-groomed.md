**Correction: "the Admin API is not exposed, so this is Paul's" was a wrong
inference.** The read-only Data API genuinely cannot mark a key event - but the
task never required an API. GA4's own UI does it: **Admin → Data display →
Events → Create event → "Create with code"**, which takes an event name plus a
"Mark as key event" toggle and needs no already-received data. (The star on the
Events list *does* require received data, which is what made this look blocked:
`contact_cta_click` had fired **zero** times, since it only shipped 2026-08-20
in PR #474.) Third instance in one day of the same mistake - inferring a
capability limit instead of checking. The rule generalises past tools to UIs:
**exhaust the interface before declaring something blocked.**

Two configuration notes for whoever audits this later:
- The create dialog **pre-selects a $1 default key-event value.** Left alone it
  would have booked phantom revenue on every contact click. Set to "Don't set a
  default key event value".
- Counting method left at GA4's recommended **"Once per event"** rather than
  once-per-session: per-event keeps the raw signal, and reporting can always
  dedupe to sessions afterwards, but it cannot un-dedupe.

The handler itself was verified live in the deployed HTML before any of this -
it listens on `a[href*="/contact-us"]` and calls
`gtag("event","contact_cta_click", …)`. The metric reads zero because nobody has
clicked a contact CTA yet, not because the instrumentation is broken. **No
synthetic event was fired to unblock the UI** - a fabricated first data point in
a conversion series whose true count is zero would have been worse than waiting.
